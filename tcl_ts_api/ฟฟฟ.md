# แกะแอป TCL Home มาทำเป็น API เพื่อสั่งแอร์จาก Siri

เรื่องมันเริ่มจากความขี้เกียจล้วนๆ ครับ

ผมมีแอร์ TCL ที่คุมผ่านแอป "TCL Home" ได้ แต่พอวันหนึ่งอยากให้มันง่ายขึ้น เช่นตั้ง automation ให้เปิดก่อนถึงบ้าน, หรือสั่งด้วยเสียงผ่าน Siri ปรากฏว่า TCL ไม่เปิด public API ให้, ไม่มี integration, ไม่มี webhook อะไรสักอย่าง

ทางเดียวที่เหลือคือ เลียนแบบสิ่งที่แอปมือถือทำ แล้วห่อมันเป็น HTTP API ธรรมดาที่ระบบอื่นเรียกใช้ได้
ฟังดูเหมือนงานเย็นๆแต่ไม่เลยครับ

## พอแกะเข้าไปจริง มันไม่ใช่ "login แล้วยิง endpoint เปิดแอร์"
สิ่งที่ผมคิดไว้ตอนแรกคือ login เอา token แล้วยิง endpoint สั่งเปิด จบ

ความจริงคือ flow มันซ้อนกันหลายชั้นมาก:
1. Login บัญชี TCL (HA auth) — รหัสผ่านถูกส่งเป็น MD5 พร้อม header แปลกๆ อย่าง th_platform, th_version, th_appbulid ที่ปลอมตัวว่าเป็นแอป Android
2. ขอ cloud URL — ต้องเรียก endpoint แยกอีกตัว เอา SSO token ไปหาว่า user นี้อยู่ region ไหน cloud ไหน
3. loadBalance — ขั้นนี้ได้ Cognito identity, MQTT endpoint และ token ชุดใหม่กลับมา โดยต้องแนบ header Sign = md5(timestamp + nonce + accessToken) ที่ต้องคำนวณใหม่ทุกครั้ง
4. AWS Cognito — เอา identity ไปแลกเป็น AWS credentials ชั่วคราว
5. AWS IoT Device Shadow — สถานะแอร์ไม่ได้อ่าน/เขียนผ่าน REST ตรงๆ แต่ต้องคุยผ่าน shadow topic ของ AWS IoT

สรุปคือแอป TCL Home มันไม่ใช่ client ที่คุยกับ backend ธรรมดา แต่มันเป็น mobile client ที่คุยกับ AWS IoT ผ่าน Cognito อีกที

## บทเรียนที่เจ็บที่สุด: เรื่อง token หมดอายุ
ด่านที่ทำให้ปวดหัวที่สุดไม่ใช่ตอน login แต่เป็นตอนใช้งานต่อเนื่อง
AWS credentials ที่ได้จาก Cognito มันเป็น temporary credentialsมีอายุสั้นแล้วหมดอายุได้ พอหมดปุ๊บ การอ่าน shadow ก็พังทันที ขึ้น error ที่ดูเหมือนไม่เกี่ยวกัน (เช่น region ผิด หรือ endpoint หาไม่เจอ) ทั้งที่จริงต้นเหตุคือ creds มันแตกไปแล้ว

จุดนี้แหละที่โปรเจกต์ reverse-engineer ตัวอื่นที่ทำมาก่อน อย่าง [ha-tcl-home-unofficial-integration ของ nemesa](https://github.com/nemesa/ha-tcl-home-unofficial-integration) ก็เจอเหมือนกัน มันเป็น integration สำหรับ Home Assistant ที่ก็เกิดจากการแกะแอป TCL Home Android ตัวเดียวกัน 

ทางแก้คือต้องแยกให้ชัดระหว่าง session ที่ cache ได้ กับ credentials ที่ต้อง refresh เมื่อใกล้หมดอายุ เก็บ token ไว้ใช้ซ้ำแล้วต่อ refresh เฉพาะตอนที่มันจะหมดจริงๆ ไม่ใช่ทุกครั้งที่ยิงคำสั่ง

(เกร็ดเล็กๆ จากฝั่ง nemesa: เขาแนะนำให้สร้าง user TCL ใหม่แยกต่างหากแล้วแชร์อุปกรณ์มาให้ user นั้น เผื่อวันหนึ่ง TCL ตัดสินใจแบนบัญชีที่ใช้แกะ — บัญชีหลักจะได้ไม่โดนไปด้วย เป็นคำแนะนำที่ควรทำตามจริงๆ)

## เครื่องมือที่ใช้แกะ
- ดัก traffic ด้วย Burp — จับ request จริงตอนกดเปิด/ปิดแอร์ในแอป เพื่อดู URL, header, body ที่แอปส่งออกไป
- decompile APK ด้วย jadx — ไล่อ่านโค้ดหา endpoint, ชื่อ field, และ logic การ sign กับการแปลงรหัสผ่านเป็น MD5
- ยิงซ้ำทีละชั้น — login → cloud URL → loadBalance → Cognito → shadow ทำให้แต่ละ step ผ่านก่อนค่อยขยับไปต่อ
- เก็บค่าที่เปราะไว้ที่เดียว — version กับ User-Agent ที่พังง่ายเมื่อแอปอัปเดต ผมรวมไว้ในไฟล์เดียว (`src/env.ts`) เวลา TCL ออกแอปใหม่จะได้แก้จุดเดียวจบ

## ปลายทาง: REST API ที่เรียกง่ายๆ
สุดท้ายผมห่อทุกอย่างไว้เป็น Bun HTTP server ที่ซ่อนความยุ่งเหยิงทั้งหมดไว้ข้างใน เหลือออกมาเป็น REST ที่ใครก็เรียกได้:
- `GET /api/ac/status` — อ่านสถานะแอร์
- `POST /api/ac/power` — ส่ง `{ "on": true }` เพื่อเปิด/ปิด
- `POST /api/ac/temperature` — ส่ง `{ "value": 25 }` หรือ `{ "delta": -1 }`
- `GET /health` — เช็คว่า server ยังอยู่ดี

session เก็บลงไฟล์อัตโนมัติ login ครั้งแรกครั้งเดียวแล้วใช้ต่อได้เลย จากนั้นเอาไปผูกกับ Home Assistant, Siri (ผ่าน `rest` command), Node-RED, cron หรืออะไรก็ได้ที่ยิง HTTP เป็น


หมายเหตุ: โปรเจกต์นี้ไม่ใช่ของ official TCL เป็นงานส่วนตัวที่ทำเพื่อใช้เอง ใครจะลองทำตามโปรดประเมินความเสี่ยงเอง บัญชีอาจโดน rate-limit ได้ถ้ายิงถี่เกินไป และอย่า expose port ออก internet ตรงๆ เพราะ config มีรหัสผ่านอยู่
